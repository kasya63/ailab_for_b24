# AI Lab (local.ailab) 1.3.1

Что умеет модуль сейчас:

- **Этап 1.** Хранить подключения к провайдерам ИИ (Anthropic и OpenAI-совместимые: OpenAI, OpenRouter и др.), шифровать API-ключи и проверять подключение пробным запросом со строгим JSON-ответом.
- **Этап 2.** Сценарии: инструкция для модели, источники данных (элементы CRM, смарт-процессов и списков, SQL, текст), формат ответа с серверной проверкой и тестовый прогон из админки — на реальном элементе или на данных, введённых руками.
- **Этап 3.** Очередь и фоновый обработчик (cron): параллельная отправка, повторы при временных сбоях, сторож зависших задач, сроки ожидания, суточный лимит; журнал всех запросов с промтом, ответами провайдера и токенами.
- **Этап 4.** Кубик «AI Lab: запрос к ИИ» для дизайнера бизнес-процессов: ставит задачу в очередь, ждёт ответа как «Пауза», отдаёт поля ответа сценария в «Дополнительных результатах».
- **Этап 5.** `UsageContext.php` рядом с UsageStats: история выбора инициатора (частые статьи и проекты, последние заявки «заявка → что выбрано») для входа `AI_CONTEXT`. Готовый боевой сценарий статей расходов.
- **Этап 6.** Файлы: PDF и картинки целиком или текстом, Word / Excel / PowerPoint — текстом через LibreOffice; лимиты размера, страниц и объёма текста.
- **Этап 7.** Предохранители и обслуживание: страница настроек, пауза очереди, защита от переполнения, уведомления администраторам, агент-сторож, ежедневная чистка журнала.

## Установка

1. Распакуйте архив в `/home/bitrix/www/local/modules/` так, чтобы получилось `/home/bitrix/www/local/modules/local.ailab/include.php`.
2. Если заливали под своей учёткой, верните владельца:
   `chown -R bitrix:bitrix /home/bitrix/www/local/modules/local.ailab`
3. Админка → Marketplace → Установленные решения → «AI Lab» → Установить.

Установщик:
- создаёт таблицы `local_ailab_*`;
- создаёт каталог `/home/bitrix/.ailab/` (права 700) и ключ шифрования `secret.key` (права 600) — вне веб-корня;
- копирует страницы модуля `/bitrix/admin/ailab_*.php`.

Папка `/home/bitrix/www/local/ailab`, созданная заранее, модулю не нужна.

## Первое подключение

Сервисы → AI Lab → Подключения → Добавить подключение → «Сохранить и проверить».

| Провайдер | Адрес API | Модель | Вкладка «Дополнительно» |
|---|---|---|---|
| Anthropic | пусто | `claude-haiku-4-5-20251001` | ничего менять не нужно |
| OpenAI | пусто | из кабинета OpenAI | для новых моделей «Поле лимита токенов» = `max_completion_tokens`; у reasoning-моделей снять «Передавать temperature» |
| OpenRouter | `https://openrouter.ai/api/v1` | как в каталоге OpenRouter, например `anthropic/claude-haiku-4.5` | обычно ничего |

Проверка показывает статус, время, токены, разобранный JSON, а также запрос и ответ провайдера целиком (ключ в запрос не попадает: он уходит только в заголовке). Если провайдер ругается на параметр, под ошибкой появится подсказка, какую настройку сменить.

## Ключ шифрования — в бэкап

`/home/bitrix/.ailab/secret.key` нужен, чтобы расшифровать API-ключи из базы. Выгрузка одной только базы ключи не раскрывает. Если файл потеряется (например, при переезде без каталога `/home/bitrix`), ключи API нужно будет ввести заново — сами подключения сохранятся.

Другой путь для каталога можно задать до установки в `/local/php_interface/init.php`:

```php
define('LOCAL_AILAB_PRIVATE_DIR', '/путь/вне/www');
```

## Удаление

Удаление модуля убирает страницы из `/bitrix/admin`, заглушки кубика из `/local/activities`, агент-сторож и регистрацию модуля. Таблицы `local_ailab_*` и ключ шифрования остаются, так что при переустановке ничего не теряется. Полностью стереть данные — вручную: `DROP TABLE local_ailab_task, local_ailab_prompt, local_ailab_source, local_ailab_scenario, local_ailab_connection;` и удалить `/home/bitrix/.ailab/`.

## Дополнительные параметры запроса

В подключении на вкладке «Дополнительно» есть поле «Дополнительные параметры запроса» — JSON-объект, который добавляется в тело каждого запроса. Для GPT-5 nano на задачах выбора из справочника подходит:

```json
{"reasoning_effort": "low"}
```

Меньше рассуждений — быстрее ответ и меньше выходных токенов. Модель, сообщения и формат ответа модуль задаёт сам, перезаписать их отсюда нельзя. Если провайдер не знает параметр, «Проверить подключение» покажет ошибку с подсказкой.

## Сценарии

Сценарий — это всё, что нужно для одного типа вопроса к ИИ: подключение, инструкция, данные и формат ответа. Бизнес-процесс будет вызывать сценарий по коду (например `expense_check`).

Промт всегда собирается в одном порядке:

| Часть | Что внутри | Откуда |
|---|---|---|
| system | 1. Инструкция → 2. «# Данные» (источники по порядку) → 3. «# Формат ответа» | настройки сценария; одинаково для всех заявок, кэшируется у провайдера |
| user | 4. Кусок промта из кубика → 5. «# Входные данные» с типами и пояснениями | то, что передаст кубик (в тестовом прогоне — форма) |

Предохранители сценария: лимит размера промта (при превышении запрос не уходит, кубик получит ошибку) и лимит запросов в сутки (см. «Очередь и обработчик»).

### Формат ответа

Каждое поле становится результатом кубика в дизайнере БП. Типы:

| Тип | Что вернёт модель | Проверка на сервере |
|---|---|---|
| Строка, целое, число, да/нет | значение | тип; «12» → 12, «true» → true |
| Один из вариантов | строка из списка | только из списка (регистр не важен) |
| ID из источника | целое число | ID должен быть среди строк, реально ушедших в промт; можно разрешить 0 — «ничего не подошло» |
| Список ID из источника | массив целых | чужие ID отбрасываются, дубли убираются, лишние сверх «не больше N» обрезаются — с пометкой |
| Таблица (строки с колонками) | массив объектов по колонкам | схема строгая; ID в каждой ячейке сверяются с источником (см. ниже) |

### Тип «Таблица»

Для распределений: сотрудники, проекты, периоды с суммами. Колонки описываются в «Настройках типа», по одной в строке:

```
код | тип | источник | описание для модели
```

Типы колонок: `строка`, `число`, `дата` (вернётся ДД.ММ.ГГГГ), `id` (нужен заголовок источника с ID).
`id*=article_project_id` — пустые после проверки ячейки (модель не нашла, вернула 0 или чужой ID) получают ID из поля ответа `article_project_id`; в журнал пишется, в скольких строках сработало.
Звёздочка после типа (`id*`, `строка*`, `число*`) делает колонку обязательной: модели запрещён null, и «уклониться» пустым значением она не может. Чужой ID в такой колонке всё равно превращается в null с предупреждением.
Ячейка `id` приходит объектом `{"id": …, "title": "…"}`. Ячейка без валидного ID (null, 0, ID не из промта) становится пустой целиком, а в журнал пишется предупреждение — ответ целиком не бракуется.
Числа понимают «₸12,300» = 12300 и «1 234,56». Полностью пустые строки выкидываются; «не больше N строк» обрезает лишнее с пометкой.

В бизнес-процесс таблица уходит результатом типа «Текст» — JSON `{"rows":[…]}`. Этот формат напрямую принимает модуль `local.bptable` (переменная или поле типа «Таблица распределения»).

Все поля передаются модели как обязательные (так требует строгий режим OpenAI); у необязательных допустим `null`. Коды `status`, `error_text`, `log_id`, `attempts` заняты служебными результатами кубика.

Если ответ не прошёл проверку, модуль один раз переспрашивает модель, перечислив ошибки и приложив её прошлый ответ. Не прошёл и второй раз — статус `invalid`, бизнес-процесс берёт запасной вариант.

### Источники

| Тип | Что делает | Даёт ID для ссылок |
|---|---|---|
| Элементы CRM, смарт-процесса, списка или HL-блока | выбранные поля, фильтр, сортировка, лимит строк | да, ID элемента или записи |
| SQL-запрос | один SELECT через подключение только на чтение | да, из указанной колонки |
| Текст | правила, памятки, небольшие справочники как есть | нет |

**HL-блоки** (с 1.1) — в том же выборе сущности, группа «Highload-блоки», с русским названием блока, если оно задано. Поля — ID и пользовательские поля блока (`UF_*`); фильтр, параметры, сортировка и лимит работают так же, как для CRM. Привязка к элементу другого HL-блока показывается значением поля, выбранного для отображения в настройках привязки («Казахстан (#1)»). Запись HL-блока можно взять и в тестовом прогоне — в «Полях реального элемента».

Значения приходят модели в человеческом виде: пользователь → ФИО и должность, вариант списка → его название, привязка к CRM → название элемента и тип, деньги → «150000 KZT», даты → 01.10.2026. Поля незнакомых типов выводятся как есть. Длинные значения обрезаются до 2000 символов.

**Лимит строк — без молчаливой обрезки.** Если источник вернул больше строк, чем разрешено, запрос не уходит, а кубик получит ошибку с текстом «сузьте фильтр или поднимите лимит». Иначе модель выбирала бы из неполного справочника и не знала об этом.

**Параметры.** В фильтре значение `:org_id` (целиком) или в SQL `WHERE X = :org_id` — это параметр: в бизнес-процессе его заполнит кубик, в тестовом прогоне — поле формы. Подставляется только экранированным значением.

Кнопка «Проверить источник» выполняет источник без сохранения и показывает число строк, размер, предупреждения и то, как данные увидит модель.

## Тестовый прогон

AI Lab → Сценарии → «Тестовый прогон»:

- **Поля реального элемента** — выберите сущность (например СП «Заявки на оплату»), ID и нужные поля: значения возьмутся в том же человекочитаемом виде, в каком их передаст кубик.
- **Дополнительные входные данные** — то, чего нет в полях элемента: ID статьи от скрипта, AI_CONTEXT с историей и т.п.
- **Параметры источников** и **кусок промта из кубика**.

«Показать промт» собирает запрос, ничего не отправляя: видны оба блока промта, JSON Schema, размер по источникам и грубая оценка в токенах. «Отправить в ИИ» делает настоящий запрос: результат, который получил бы бизнес-процесс, ошибки проверки, все попытки с сырым запросом и ответом. Введённые данные запоминаются для сценария.

## Очередь и обработчик

Бизнес-процесс (этап 4) и кнопка «Поставить в очередь» на странице тестового прогона кладут задачу в очередь и сразу освобождаются. Отправляет задачи фоновый обработчик `tools/worker.php`, который cron запускает раз в минуту.

### Подключить обработчик

Под root откройте cron пользователя сайта и добавьте строку рядом со строкой `cron_events.php` Битрикса:

```bash
crontab -u bitrix -e
```

```
* * * * * /usr/bin/php -f /home/bitrix/www/local/modules/local.ailab/tools/worker.php >/dev/null 2>&1
```

Проверить вручную, с подробным выводом и состоянием очереди:

```bash
sudo -u bitrix php -f /home/bitrix/www/local/modules/local.ailab/tools/worker.php -- -v
sudo -u bitrix php -f /home/bitrix/www/local/modules/local.ailab/tools/worker.php -- --status
```

Запускать только от `bitrix`: от root обработчик откажется работать, потому что файлы кэша, созданные root, сайт потом не сможет перезаписать. Если cron не настроен или обработчик молчит дольше 5 минут, «Журнал» и карточка задачи покажут предупреждение с этой же строкой для cron.

### Как он работает

- **Один экземпляр.** Файловая блокировка (`/home/bitrix/.ailab/worker.lock`): пока работает один запуск, следующие сразу выходят. Если процесс упал, блокировку снимает ОС.
- **Каждая задача уходит один раз.** Задача забирается атомарно (`UPDATE … WHERE STATUS = 'pending'`), поэтому два процесса не могут отправить её одновременно. Повторная отправка бывает только по правилам ниже, и каждая видна в журнале.
- **Параллельно.** До 3 запросов одновременно (curl_multi). Пачка из трёх длится столько, сколько самый долгий запрос, а не сумма.
- **Пустая очередь — сразу выход.** Новые задачи обработчик набирает первые 50 секунд запуска, начатые доводит до конца. Если ближайший отложенный повтор наступает в пределах этого окна, обработчик дожидается его, а не следующего запуска cron.
- **Промт собирается один раз,** когда задача впервые берётся в работу. Повторы уходят с тем же промтом и проверяются по тем же ID. Постоянная часть промта хранится один раз на все задачи (`local_ailab_prompt`), поэтому журнал не раздувается справочником в каждой строке.

| Что пришло от провайдера | Что делает обработчик |
|---|---|
| Ответ прошёл проверку | `success` |
| Ответ не по формату или не прошёл проверку (например, чужой ID) | сразу переспрашивает с перечнем ошибок; не помогло — `invalid` |
| 429, 5xx, таймаут, сетевой сбой | повтор через 15 с, потом через 60 с; всего 3 попытки, затем `error` |
| Повтор не успевает до конца срока ожидания | `timeout` |
| 400, 401, 403, 404 | `error` без повторов: повтор не поможет |

**Сторож.** Задача, которая провисела в «отправлено» дольше 10 минут (обработчик упал посреди запроса), возвращается в очередь, если попытки не исчерпаны. Иначе она получает `error`. Задача, не дождавшаяся отправки за срок ожидания (по умолчанию 10 минут), получает `timeout`.

**Суточный лимит** сценария считает задачи из бизнес-процессов с начала суток. При превышении задача не ставится, а кубик (этап 4) сразу получит ошибку. Тестовые задачи не считаются.

**Событие.** По завершении задачи модуль отправляет событие `local.ailab:OnTaskFinished` с параметрами `ID` и `STATUS`, а затем будит бизнес-процесс, если задачу поставил кубик.

## Журнал

«AI Lab → Журнал» показывает:

- состояние обработчика;
- сводку за период: сколько задач в каждом статусе и сколько токенов ушло, в том числе прочитанных из кэша;
- список задач с фильтром по сценарию, статусу, источнику и номеру.

В карточке задачи собрано всё, что нужно для разбора:

- итог и результат, который получит бизнес-процесс;
- каждое обращение к провайдеру: HTTP-код, время, токены, ошибки проверки и сырой ответ;
- входные данные, промт целиком и JSON Schema.

Пока задача не завершилась, карточка обновляется сама раз в 5 секунд; задачу в очереди можно отменить.

## Кубик бизнес-процесса

В дизайнере БП: «Прочее → AI Lab → AI Lab: запрос к ИИ». Заглушки в `/local/activities/ailabrequestactivity/` только подключают код из модуля, поэтому обновление модуля обновляет и кубик.

### Настройки

- **Сценарий** — из списка AI Lab. Под ним видно, какие результаты будут у кубика и какие параметры источников нужно заполнить.
- **Поля документа** — галочками; для CRM, смарт-процессов и списков. Значения уходят модели в том же человекочитаемом виде, что в тестовом прогоне.
- **Дополнительные входы** — название (обычный текст: так модель увидит вход), пояснение для модели и значение через кнопку «…»: переменная, поле, результат другого действия. Например «Предложенная статья (ID)» = `EXPENSE_ID`, «История пользователя» = `AI_CONTEXT`. Пустое название подставится из имени переменной. Если переменную по ошибке поставили в «Название», а «Значение» оставили пустым, кубик сам перенесёт её в значение.
- **Параметры источников** — строки появляются сами, если источники сценария используют `:параметр`.
- **Кусок промта** — уточнение для этого места процесса, уходит перед входными данными.
- **Поля-файлы** — что делать с отмеченными полями типа «файл»: только имя (по умолчанию), содержимое текстом или PDF и картинки целиком. Подробности — в разделе «Файлы».
- **Ждать ответа не дольше** — по умолчанию 10 минут.
- **Комментарий в таймлайн** — только для CRM: по завершении в таймлайн элемента пишется итог.

### Результаты

| Результат | Что внутри |
|---|---|
| `status` | `success`, `error`, `invalid` (ответ не прошёл проверку и после исправления) или `timeout` |
| `error_text` | почему не `success` |
| `log_id` | номер задачи в «AI Lab → Журнал» |
| поля ответа сценария | в «Дополнительных результатах»: строки, числа, `Y`/`N` для «да/нет», массивы ID для «Списка ID» |

При `status ≠ success` поля ответа пустые — ведите процесс по запасной ветке. Поменяли формат ответа в сценарии — откройте кубик и сохраните, чтобы дизайнер увидел новые поля.

### Как кубик ждёт

1. Кубик собирает входы, ставит задачу (первая отправка — через 3 секунды, чтобы процесс успел сохраниться) и засыпает. В журнал БП пишется «запрос №N поставлен в очередь».
2. Обработчик очереди получает ответ и будит процесс (`CBPRuntime::sendExternalEvent`), как это делает Битрикс по завершении задания. Продолжение процесса выполняется в том же запуске обработчика.
3. Кубик читает итог из журнала задач, заполняет результаты и пишет в журнал БП статус, время, токены и сводку ответа.

Если разбудить процесс не удалось (например, он в этот момент сохранялся), обработчик повторяет попытку при следующих запусках, до 5 раз. Кроме того, кубик ставит страховочный таймер Битрикса на «срок ожидания + 2 минуты»: если cron мёртв или все попытки пробуждения сорвались, таймер разбудит процесс. Кубик сам заберёт готовый ответ из журнала, а если ответа нет — вернёт `timeout` и снимет задачу.

Неизвестный или выключенный сценарий, исчерпанный суточный лимит, ошибка источника — кубик сразу завершается со `status = error`, процесс идёт дальше. Остановили процесс, пока задача ждала, — задача снимается из очереди.

### Пример: проверка статьи расходов

```
[PHP-код: UsageStats]  → PROJECT_ID, EXPENSE_ID, AI_CONTEXT (этап 5)
[AI Lab: запрос к ИИ]  сценарий expense_check
                        поля документа: назначение платежа, сумма, контрагент
                        входы: «Предложенная статья (ID)» = EXPENSE_ID, «История пользователя» = AI_CONTEXT
[Условие]              {=A…:status} = success и {=A…:article_id} > 0
   да  → EXPENSE_ID = {=A…:article_id}, в комментарий задания — {=A…:reason}
   нет → оставить EXPENSE_ID от скрипта
[Задание сотруднику на проверку]
```

## Файлы

Где включается: в кубике — «Поля-файлы» для отмеченных полей документа типа «файл»; в тестовом прогоне — тот же выбор под полями элемента. По умолчанию уходит только имя файла.

| Формат | «Текстом» | «Целиком» |
|---|---|---|
| PDF с текстом | текст (`pdftotext -layout`, раскладка таблиц сохраняется) | PDF вложением: модель видит страницы, печати, сканы |
| PDF-скан без текста | автоматически вложением, с пометкой в журнале | вложением |
| JPG, PNG, GIF, WEBP | вложением (картинку в текст не перевести) | вложением |
| Word, RTF, ODT, PowerPoint | текст: LibreOffice → PDF → текст | так же текстом |
| Excel, ODS | текст: все листы, ячейки через «\|» (LibreOffice → HTML) | так же текстом |
| TXT, CSV, JSON, XML, HTML | как есть; cp1251 перекодируется в UTF-8 | так же |

Текст файла попадает в раздел «# Файлы» данных заявки, вложения идут после текста; в промте указано, какое вложение к какому полю относится. Работает с обоими провайдерами: OpenAI получает PDF как `file`, картинки как `image_url`; Anthropic — `document` и `image`.

Стоимость: страница PDF целиком — примерно 1–2 тыс. токенов, текстом — в разы меньше. Предпросмотр промта показывает по каждому файлу, как он уйдёт, и оценку токенов для PDF целиком. Для выбора статьи расходов файлы не нужны; включайте их там, где без документа модель не справится (разбор счёта, проверка договора).

Лимиты («AI Lab → Настройки → Файлы»): размер файла, размер картинки (у Anthropic 5 МБ), страниц PDF целиком, символов текста, файлов в запросе. Превышение — ошибка с понятным текстом, а не молчаливая обрезка.

В очереди содержимое файлов не хранится: текст попадает в сохранённый промт задачи, а PDF и картинки берутся из файла заново при каждой отправке (в том числе при повторе после 429). Если файл удалили до отправки, задача завершится ошибкой «файл не найден».

Конвертация Office идёт во временном каталоге с отдельным профилем LibreOffice на каждый вызов — параллельные задачи не мешают друг другу, мусор удаляется. Нужна функция PHP `proc_open` (обычно включена); если она отключена, ошибка скажет об этом прямо.

## Настройки и предохранители

«AI Lab → Настройки»:

| Раздел | Что настраивается |
|---|---|
| Очередь | пауза очереди; запросов одновременно (3); ожидание по умолчанию (10 мин); задач в очереди не больше (300) |
| Журнал | хранить задачи, дней (90) |
| Файлы | лимиты из раздела «Файлы»; пути к soffice, pdftotext, pdfinfo |
| Уведомления | уведомлять администраторов (вкл.) |

Кнопки: «Проверить инструменты для файлов» — запускает soffice / pdftotext / pdfinfo от пользователя сайта и показывает версии; «Почистить журнал сейчас».

**Пауза очереди** — на время проблем у провайдера или обслуживания: обработчик не отправляет новые задачи; ждущие получат «время вышло» по своему сроку, и процессы пойдут по запасной ветке.

**Защита от переполнения.** Если в очереди ждут больше заданного числа задач (зациклившийся процесс или умерший обработчик), новые не принимаются: кубик сразу получает `status = error`.

**Уведомления** приходят в мессенджер администраторам портала, не чаще раза в час по каждому поводу:

- провайдер отклоняет запросы подключения (HTTP 401, 403, 404 — ключ или модель);
- задачи ждут, а обработчик очереди молчит — это проверяет агент-сторож `\Local\AiLab\Agent::watchdog()` раз в 5 минут, через агенты Битрикса, независимо от нашего cron;
- исчерпан суточный лимит сценария (не чаще раза в 6 часов);
- очередь переполнена;
- бизнес-процесс не удалось продолжить после 5 попыток.

**Чистка журнала** — раз в сутки в обработчике очереди: завершённые задачи старше срока хранения и постоянные части промтов, на которые больше никто не ссылается. Задачи в очереди не трогаются.

## История инициатора для ИИ (UsageContext)

Файл `UsageContext.php` кладётся рядом с UsageStats: `/local/php_interface/bp/UsageContext.php`. UsageStats не меняется: смарт-процессы, исключённые поля и лимит анализа UsageContext берёт из его констант, значения полей форматирует модулем AI Lab — так же, как кубик.

Что получает модель:

```
Проанализировано прошлых заявок инициатора: 37 (текущая не учитывается).

Статьи расходов, которые инициатор выбирал чаще всего (заполнено в 30 заявках):
1. #12 «Аренда офиса» — 10 раз, последний раз в заявке #214518
2. #20 «Канцелярия» — 4 раз, последний раз в заявке #214519

Проекты, которые инициатор выбирал чаще всего (заполнено в 30 заявках):
1. #449 «Smart Cargo» — 25 раз, последний раз в заявке #214520

Последние заявки инициатора (новые сверху): заявка → что выбрано.
- #214520 «Оплата аренды за октябрь» (Назначение: аренда офиса) → статья #12 «Аренда офиса»; проект #449 «Smart Cargo»
```

Удалённые из справочника статьи в «чаще всего» не показываются. Если истории нет — так и сказано одной фразой.

В PHP-блоке БП, после вызова UsageStats (переменную `AI_CONTEXT` типа «Строка» объявите в шаблоне — иначе `SetVariable` молча не сработает):

```php
$root = $this->GetRootActivity();
require_once $_SERVER['DOCUMENT_ROOT'] . '/local/php_interface/bp/UsageContext.php';
// $params — тот же массив, что вы отдаёте UsageStats::run()
$root->SetVariable('AI_CONTEXT', \Local\Bp\UsageContext::build($params + [
    'history_fields' => [],   // по желанию: ['PROPERTY_КОД'] — поля заявки в строке истории, кроме названия
]));
```

Параметры сверх UsageStats: `history_fields` (поля для истории; для списков — `PROPERTY_<КОД>` или `PROPERTY_<ID>`, для CRM — код поля), `history` (сколько заявок, 15), `format` (`text` или `json`). `build()` не бросает исключений: при сбое вернёт строку с причиной, процесс пойдёт дальше.

## Первый боевой сценарий: статьи расходов

**Сценарий `expense_check`.** Модель — `gpt-5-nano` в поле «Модель» сценария (подключение не меняется); перед переключением прогоните тестом 5–10 реальных заявок на gpt-5.1 и на nano и сравните. В подключении — `{"reasoning_effort": "low"}`.

Инструкция:

```
Ты — финансовый контролёр группы компаний. По заявке на оплату определи статью расходов
из справочника «Статьи расходов».

Как решать:
1. Главное — смысл заявки: что оплачивают, у кого, для какого проекта. Название, обоснование
   и контрагенты важнее истории.
2. «Статья от скрипта» — статья, которую инициатор чаще всего выбирал раньше. Это подсказка,
   а не истина: инициатор может оплачивать что-то новое. 0 — скрипт ничего не нашёл.
3. «История выбора инициатора» показывает, какие статьи он ставил на похожие заявки.
   Используй её, когда смысл заявки допускает несколько статей.
4. Статья от скрипта подходит по смыслу — confirmed и её ID. Не подходит — replaced и ID
   подходящей. Скрипт дал 0 — selected. В справочнике нет подходящей — not_found и 0.
5. Выбирай только из справочника. Подходят несколько — выбери самую конкретную,
   остальные укажи в alternatives.
```

Источник: элементы «Статьи расходов (150)», поле «Название» (и «Описание для ИИ», когда заполните), лимит 500.

Формат ответа:

| Код | Тип | Описание для модели |
|---|---|---|
| `decision` | Один из вариантов: confirmed, replaced, selected, not_found | confirmed — статья от скрипта подходит; replaced — скрипт предложил неподходящую, выбрана другая; selected — скрипт ничего не дал (0), выбрана с нуля; not_found — в справочнике нет подходящей |
| `article_id` | ID из источника «Статьи расходов», галочка «0 — ничего не подошло» | — |
| `reason` | Строка | 1–2 предложения по-русски для сотрудника, проверяющего заявку: почему эта статья |
| `alternatives` | Список ID из источника, не больше 3, необязательное | 2–3 следующие по смыслу статьи, без выбранной; пусто, если других нет |

**Кубик в копии шаблона.** Поля документа: название, продавец, покупатель, группа компаний, проект, подробное обоснование, тип расходов; поле-файл не отмечать (режим «только имя» или снять галочку). Дополнительные входы: «Статья от скрипта (ID), 0 = не найдена» = `EXPENSE_ID`; «История выбора инициатора» = `AI_CONTEXT`. Ждать — 10 минут.

**Дальше в процессе:**

```
[Условие] {=A…:status} = success и {=A…:article_id} > 0
   да  → статья = {=A…:article_id}; в задание проверяющему — {=A…:reason}
   нет → статья от скрипта (EXPENSE_ID), в задание — «ИИ не ответил: {=A…:error_text}»
[Задание сотруднику на проверку]
```

Обкатка: копия шаблона на реальных заявках; в «AI Lab → Журнал» фильтр по сценарию показывает, сколько заявок и токенов ушло, а карточка каждой задачи — что видела модель и почему ответила так.

## SQL-источник: подключение только на чтение

SQL-источник работает через отдельного пользователя MySQL с единственным правом SELECT. Проверка запроса в модуле (только SELECT/WITH, без «;», комментариев, INTO, блокировок) — второй рубеж, а не первый.

1. Имя базы посмотрите в `/home/bitrix/www/bitrix/.settings.php`, ключ `connections → default → database` (на BitrixVM обычно `sitemanager`).
2. Создайте пользователя (под root MySQL):

   ```sql
   CREATE USER 'ailab_ro'@'localhost' IDENTIFIED BY 'длинный-случайный-пароль';
   GRANT SELECT ON sitemanager.* TO 'ailab_ro'@'localhost';
   ```

3. Сделайте копию `/home/bitrix/www/bitrix/.settings.php` и добавьте второе подключение рядом с `default`:

   ```php
   'connections' => [
       'value' => [
           'default' => [
               // как было, не трогать
           ],
           'ailab_readonly' => [
               'className' => '\Bitrix\Main\DB\MysqliConnection',
               'host'      => 'localhost',
               'database'  => 'sitemanager',
               'login'     => 'ailab_ro',
               'password'  => 'длинный-случайный-пароль',
               'options'   => 2,
           ],
       ],
       'readonly' => true,
   ],
   ```

4. Проверьте: на вкладке «Источники» сценария пропадёт предупреждение о ненастроенном подключении, а «Проверить источник» на `SELECT ID, TITLE FROM b_crm_dynamic_items_150` покажет строки.

Каждый запрос выполняется не дольше 5 секунд (подсказка `MAX_EXECUTION_TIME`, MySQL 5.7.8+) и оборачивается в `SELECT * FROM (…) LIMIT n`, так что лимит строк соблюдается при любом тексте запроса. Таблицы смарт-процессов называются `b_crm_dynamic_items_<entityTypeId>`.

```
        ├── OutputSchema.php                 формат ответа: JSON Schema, описание, проверка
        ├── PromptBuilder.php                сборка промта (вместе с файлами)
        ├── ElementInputs.php                поля элемента → входы (общие для кубика и теста)
        ├── Runner.php                       отправка + проверка + один повтор
        └── Source/                          Entity-, Sql- (SqlGuard), StaticSource
```

## Как модуль добивается строгого JSON

- **Anthropic** — схема передаётся как инструмент, который модель обязана вызвать (`tool_choice`). Работает на всех моделях Claude.
- **OpenAI-совместимые** — `response_format` с JSON Schema (strict), либо упрощённые режимы для провайдеров, которые его не знают.
- **В обоих случаях** ответ дополнительно проверяется на сервере. Обрезанный ответ, отказ модели или ответ без JSON получают статус `invalid`; сетевые сбои и 429/5xx — статус `error` с пометкой, что повтор имеет смысл.
